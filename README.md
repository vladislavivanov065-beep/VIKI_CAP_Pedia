# Техническое задание: корпоративная база знаний

## 1. Общая информация

### 1.1. Название проекта

Рабочее название: **Corporate Wiki**.

Название сайта должно задаваться через переменную окружения или административные настройки.

### 1.2. Назначение системы

Разработать закрытую корпоративную базу знаний, в которой авторизованные сотрудники смогут:

* просматривать статьи;
* искать статьи;
* создавать новые статьи;
* редактировать существующие статьи;
* добавлять в статьи изображения;
* создавать ссылки на другие статьи;
* просматривать историю изменений;
* открывать любую предыдущую версию статьи;
* сравнивать версии статьи;
* видеть автора каждого изменения;
* восстанавливать старую версию статьи;
* просматривать список собственных правок.

Доступ к системе разрешён только зарегистрированным пользователям.

### 1.3. Основной стек

Backend:

* Python 3.12 или новее;
* Django;
* Django Templates;
* SQLite — стандартная база данных Django;
* Gunicorn для production-запуска;
* WhiteNoise для обслуживания статических файлов;
* Pillow для проверки и обработки изображений.

Frontend:

* HTML5;
* CSS3;
* JavaScript без отдельного SPA-фреймворка;
* Django Templates;
* адаптивная вёрстка;
* интерфейс в стиле Wikipedia Vector 2022.

Инфраструктура:

* Docker;
* Docker Compose;
* один контейнер с Django-приложением;
* SQLite-файл в постоянном Docker volume;
* изображения хранятся внутри SQLite;
* статические файлы CSS, JavaScript и системные изображения обслуживаются через WhiteNoise;
* без Nginx;
* без PostgreSQL;
* без AWS;
* без S3;
* без отдельного файлового хранилища пользовательских изображений.

Тестирование:

* pytest;
* pytest-django;
* factory_boy;
* coverage.

Качество кода:

* Ruff;
* Black;
* mypy;
* pre-commit.

# 2. Основные требования

## 2.1. Доступ к сайту

Неавторизованный пользователь может открыть только:

* страницу входа;
* служебные страницы ошибок;
* статические файлы, необходимые для отображения страницы входа.

Все статьи, история версий, изображения, поиск и пользовательские страницы должны быть недоступны без авторизации.

При попытке открыть защищённую страницу неавторизованный пользователь перенаправляется на страницу входа.

После успешного входа пользователь возвращается на страницу, которую пытался открыть.

## 2.2. Аутентификация

Вход выполняется по:

* электронной почте;
* паролю.

Имя пользователя для входа не используется.

Email должен быть уникальным без учёта регистра.

Перед сохранением email необходимо:

* удалить пробелы по краям;
* привести email к нижнему регистру;
* проверить корректность формата.

## 2.3. Первый вход

При создании пользователя администратор задаёт ему временный пароль.

У пользователя должно быть поле:

```python
must_change_password: bool
```

Для нового пользователя значение автоматически устанавливается в `True`.

После первого успешного входа пользователь должен быть принудительно перенаправлен на страницу смены пароля.

Пока пользователь не изменил временный пароль, ему разрешено открывать только:

* страницу смены пароля;
* страницу выхода;
* необходимые статические файлы.

После успешной смены пароля:

```python
must_change_password = False
```

Пользователь перенаправляется на главную страницу.

Новый пароль не должен совпадать с временным паролем.

## 2.4. Сброс пароля администратором

Самостоятельное восстановление пароля пользователем не реализовывать.

На странице входа не должно быть ссылки «Забыли пароль?».

Если пользователь забыл пароль, он должен обратиться к администратору.

Администратор устанавливает новый временный пароль через ту же административную страницу, на которой создаются и редактируются пользователи.

При установке администратором нового пароля система должна автоматически:

1. Безопасно захешировать новый пароль через механизм Django.
2. Установить:

```python
must_change_password = True
```

3. Установить дату административного сброса пароля.
4. Завершить все существующие сессии этого пользователя.
5. Записать действие в журнал аудита.
6. Не сохранять временный пароль в открытом виде.

При следующем входе пользователь обязан установить собственный новый пароль.

Администратор не должен видеть:

* текущий пароль пользователя;
* старый пароль пользователя;
* хеш пароля в редактируемом поле.

SMTP, email-сообщения, ссылки восстановления и токены восстановления пароля не требуются.

# 3. Пользователи и роли

## 3.1. Модель пользователя

Создать собственную модель пользователя на базе `AbstractBaseUser` и `PermissionsMixin`.

Обязательные поля:

```python
class User:
    id: UUID
    email: str
    first_name: str
    last_name: str
    is_active: bool
    is_staff: bool
    is_superuser: bool
    must_change_password: bool
    password_changed_at: datetime | None
    password_reset_by_admin_at: datetime | None
    last_login: datetime | None
    created_at: datetime
    updated_at: datetime
```

Не создавать поля:

```python
job_title
department
avatar
```

Методы и свойства:

```python
get_full_name()
get_short_name()
display_name
```

Если имя и фамилия не заполнены, `display_name` должен возвращать email.

## 3.2. Роли

### Обычный пользователь

Может:

* просматривать статьи;
* искать статьи;
* создавать статьи;
* редактировать статьи;
* загружать изображения;
* просматривать историю;
* сравнивать версии;
* восстанавливать предыдущие версии;
* просматривать публичную информацию о других пользователях;
* изменять собственный пароль.

Не может:

* создавать пользователей;
* блокировать пользователей;
* активировать пользователей;
* сбрасывать пароли других пользователей;
* удалять пользователей;
* изменять системные настройки;
* физически удалять историю изменений.

### Администратор

Может всё, что может обычный пользователь, а также:

* создавать пользователей;
* задавать временные пароли;
* изменять имя и фамилию пользователя;
* деактивировать пользователей;
* активировать пользователей;
* устанавливать новый временный пароль;
* принудительно включать смену пароля;
* завершать активные сессии пользователя;
* управлять статьями через Django Admin;
* архивировать статьи;
* просматривать журнал административных действий.

## 3.3. Деактивация

При деактивации пользователя:

* вход в систему блокируется;
* существующие сессии аннулируются;
* созданные им статьи и версии сохраняются;
* имя автора продолжает отображаться в истории;
* связанные записи аудита сохраняются.

Пользователей нельзя физически удалять через обычный пользовательский интерфейс.

# 4. Статьи

## 4.1. Модель Article

Создать модель статьи:

```python
class Article:
    id: UUID
    title: str
    slug: str
    current_revision: ArticleRevision | None
    created_by: User
    created_at: datetime
    updated_at: datetime
    is_archived: bool
    archived_at: datetime | None
    archived_by: User | None
    version: int
```

Ограничения:

* `title` обязателен;
* максимальная длина заголовка — 255 символов;
* заголовок уникален без учёта регистра среди неархивированных статей;
* `slug` уникален;
* `slug` генерируется автоматически;
* после переименования старый URL продолжает работать через таблицу перенаправлений;
* физическое удаление статьи из пользовательского интерфейса запрещено.

Поскольку используется SQLite, уникальность заголовка без учёта регистра необходимо обеспечить:

* проверкой в сервисном слое;
* нормализованным дополнительным полем при необходимости;
* соответствующими тестами.

## 4.2. Модель ArticleRevision

Каждое сохранение статьи создаёт новую неизменяемую версию.

```python
class ArticleRevision:
    id: UUID
    article: Article
    revision_number: int
    title: str
    content_source: str
    content_html: str
    edit_summary: str
    edited_by: User
    created_at: datetime
    restored_from: ArticleRevision | None
    content_hash: str
```

Требования:

* версии нумеруются отдельно для каждой статьи;
* первая версия имеет номер `1`;
* версии нельзя редактировать;
* версии нельзя физически удалять через интерфейс;
* `content_source` хранит исходный Markdown;
* `content_html` хранит очищенный HTML;
* `content_hash` используется для определения сохранения без изменений;
* `edit_summary` содержит краткое описание изменения;
* при восстановлении старой версии создаётся новая версия;
* восстановление не удаляет более новые версии.

## 4.3. Создание статьи

Форма создания должна содержать:

* заголовок;
* текст статьи;
* краткое описание изменения;
* кнопку загрузки изображения;
* предварительный просмотр;
* кнопку «Опубликовать»;
* кнопку «Отмена».

После создания:

1. Создаётся объект `Article`.
2. Создаётся первая `ArticleRevision`.
3. Первая версия назначается текущей.
4. Автор перенаправляется на страницу статьи.
5. Действие записывается в журнал.

## 4.4. Редактирование статьи

Форма редактирования должна содержать:

* текущий заголовок;
* текущий исходный текст;
* поле описания изменений;
* кнопку загрузки изображения;
* предварительный просмотр;
* кнопку «Сохранить изменения»;
* кнопку «Отмена».

После сохранения:

1. Проверить права пользователя.
2. Проверить актуальность открытой версии.
3. Очистить и обработать содержимое.
4. Создать новую `ArticleRevision`.
5. Увеличить номер версии.
6. Назначить новую версию текущей.
7. Обновить `Article.updated_at`.
8. Записать действие в аудит.

## 4.5. Защита от одновременного редактирования

При открытии формы редактирования передавать:

```text
base_revision_id
article_version
```

При сохранении сравнивать значения с текущей версией статьи.

Если статью уже изменил другой пользователь:

* не перезаписывать новую версию;
* показать предупреждение о конфликте;
* показать текущую сохранённую версию;
* показать вариант пользователя;
* предложить открыть сравнение;
* позволить пользователю скопировать свои изменения;
* разрешить повторное сохранение после подтверждения.

Использовать:

* `transaction.atomic()`;
* проверку номера версии;
* оптимистическую блокировку.

Не полагаться исключительно на `select_for_update()`, так как SQLite имеет ограниченную поддержку построчной блокировки.

## 4.6. Переименование статьи

При изменении заголовка:

* обновить заголовок статьи;
* создать новый slug, если это необходимо;
* сохранить старый slug в `ArticleRedirect`;
* запрос по старому URL перенаправлять на новый;
* внутренние ссылки по UUID должны продолжать работать.

## 4.7. Архивация

Вместо удаления использовать архивирование.

Архивированная статья:

* сохраняет всю историю;
* не отображается в основном поиске;
* не отображается в основном списке;
* доступна по прямой ссылке с предупреждением;
* может быть восстановлена администратором.

# 5. Формат содержимого статьи

## 5.1. Основной формат

Использовать Markdown с дополнительным синтаксисом внутренних ссылок.

Поддержать:

* заголовки;
* абзацы;
* жирный текст;
* курсив;
* зачёркнутый текст;
* маркированные списки;
* нумерованные списки;
* цитаты;
* таблицы;
* блоки кода;
* встроенный код;
* горизонтальные линии;
* внешние ссылки;
* внутренние ссылки;
* изображения;
* автоматическое оглавление.

## 5.2. Внутренние ссылки

Поддержать Wiki-синтаксис:

```text
[[Название статьи]]
```

Ссылка с другим отображаемым текстом:

```text
[[Название статьи|текст ссылки]]
```

Ссылка по UUID:

```text
[[article:UUID|текст ссылки]]
```

Поведение:

* существующая статья отображается синей ссылкой;
* несуществующая статья отображается красной ссылкой;
* переход по красной ссылке открывает форму создания статьи;
* название новой статьи автоматически подставляется в форму;
* ссылка на архивированную статью имеет отдельный индикатор.

## 5.3. Внешние ссылки

Поддержать Markdown:

```markdown
[Название сайта](https://example.com)
```

Для внешних ссылок:

* добавлять `rel="noopener noreferrer"`;
* разрешить `target="_blank"` по настройке проекта;
* отображать индикатор внешней ссылки;
* запрещать опасные URL-схемы.

## 5.4. Оглавление

Оглавление формируется автоматически из заголовков второго и третьего уровней.

Требования:

* находится слева на широких экранах;
* может сворачиваться;
* подсвечивает текущий раздел;
* содержит якорные ссылки;
* на мобильных устройствах отображается как раскрывающийся блок.

## 5.5. Очистка HTML

Пользовательский HTML по умолчанию запрещён.

Markdown преобразуется в HTML и очищается по разрешённому списку тегов и атрибутов.

Запрещены:

* `script`;
* `iframe`;
* inline JavaScript;
* обработчики событий;
* небезопасные URL;
* произвольные стили;
* формы;
* подключение внешних скриптов.

# 6. Изображения

## 6.1. Хранение изображений

Все загружаемые пользователями изображения должны храниться непосредственно в SQLite.

Не использовать:

* `ImageField` для хранения пути к файлу;
* папку `media`;
* локальное файловое хранилище;
* S3;
* AWS;
* MinIO;
* внешние файловые сервисы.

Бинарное содержимое изображения хранить в `BinaryField`.

## 6.2. Загрузка изображений

Пользователь может загрузить изображение:

* при создании статьи;
* при редактировании статьи;
* перетаскиванием в редактор;
* через кнопку «Добавить изображение».

Поддерживаемые форматы:

* JPEG;
* PNG;
* WebP;
* GIF.

SVG в первой версии запретить.

## 6.3. Ограничения

Настраиваемые ограничения:

* максимальный размер изображения — 10 МБ;
* максимальное разрешение — 8000 × 8000;
* MIME-тип проверяется по фактическому содержимому;
* расширение файла не считается достаточной проверкой;
* исходное имя хранится только как метаданные;
* изображение не сохраняется на диск.

Следует учитывать, что хранение большого числа изображений в SQLite увеличивает размер базы. Для первой версии это принимаемое архитектурное решение.

## 6.4. Модель ArticleImage

```python
class ArticleImage:
    id: UUID
    data: bytes
    thumbnail_data: bytes | None
    original_filename: str
    mime_type: str
    file_size: int
    width: int
    height: int
    alt_text: str
    caption: str
    uploaded_by: User
    uploaded_at: datetime
    checksum: str
```

Реализация полей:

```python
data = models.BinaryField()
thumbnail_data = models.BinaryField(null=True, blank=True)
```

Требования:

* бинарные данные сохраняются в базе;
* миниатюра также сохраняется в базе;
* checksum вычисляется до сохранения;
* одинаковые изображения могут переиспользоваться;
* изображение не должно жёстко принадлежать одной версии статьи.

## 6.5. Обработка

После загрузки:

1. Проверить максимальный размер.
2. Прочитать изображение через Pillow.
3. Проверить реальный формат.
4. Проверить размеры.
5. Исправить ориентацию.
6. Удалить EXIF-метаданные.
7. Повторно закодировать изображение в безопасный формат.
8. Создать миниатюру.
9. Вычислить checksum.
10. Сохранить изображение и миниатюру в базу.

## 6.6. Выдача изображения

Изображение отдаётся через отдельный Django view:

```text
/images/<uuid>/
/images/<uuid>/thumbnail/
```

View должен:

* проверять авторизацию;
* получать бинарные данные из базы;
* устанавливать правильный `Content-Type`;
* устанавливать `Content-Length`;
* поддерживать кеширующие заголовки;
* добавлять `ETag` на основе checksum;
* возвращать `404`, если изображение отсутствует.

Прямая раздача пользовательских изображений через WhiteNoise не используется.

WhiteNoise обслуживает только статические файлы приложения:

* CSS;
* JavaScript;
* системные иконки;
* системные изображения дизайна.

## 6.7. Вставка изображения

Синтаксис:

```text
![[image:UUID]]
```

С подписью:

```text
![[image:UUID|Подпись к изображению]]
```

Пользователь должен иметь возможность указать:

* альтернативный текст;
* подпись;
* выравнивание;
* размер отображения.

# 7. История изменений

## 7.1. Страница истории

URL:

```text
/articles/<slug>/history/
```

Показывать:

* номер версии;
* дату и время;
* имя автора;
* email автора только администраторам;
* описание изменения;
* размер статьи;
* разницу размера;
* отметку восстановления;
* ссылку на просмотр версии;
* выбор двух версий для сравнения.

Сортировка — от новой версии к старой.

Добавить пагинацию.

## 7.2. Просмотр старой версии

URL:

```text
/articles/<slug>/revisions/<revision_number>/
```

Показывать предупреждение:

```text

Автор изменения: Имя Фамилия.
Это не текущая версия статьи.
```

Добавить кнопки:

* «Текущая версия»;
* «Предыдущая версия»;
* «Следующая версия»;
* «Сравнить с текущей»;
* «Восстановить эту версию».

## 7.3. Сравнение версий

URL:

```text
/articles/<slug>/compare/?from=10&to=15
```

Показывать:

* данные обеих версий;
* удалённые строки;
* добавленные строки;
* изменённые фрагменты;
* изменение заголовка;
* авторов;
* даты;
* описания изменений.

Режимы:

1. Две колонки.
2. Единый текст с подсветкой.

Использовать безопасный серверный diff на основе `difflib` с обязательным HTML-экранированием.

## 7.4. Восстановление версии

При восстановлении:

* создать новую версию;
* скопировать заголовок и содержимое старой версии;
* заполнить `restored_from`;
* установить описание `Восстановлена версия №N`;
* назначить новую версию текущей;
* сохранить всю существующую историю;
* записать действие в аудит.

# 8. Поиск

## 8.1. Общий поиск

Поиск должен работать по:

* заголовкам;
* содержимому текущих версий;
* названиям разделов.

Архивированные статьи по умолчанию не включаются.

## 8.2. Реализация поиска для SQLite

Не использовать:

* PostgreSQL Full Text Search;
* `SearchVector`;
* `SearchQuery`;
* `SearchRank`;
* GIN-индексы.

Для первой версии реализовать поиск средствами Django ORM и SQLite:

* `iexact` для точного совпадения заголовка;
* `istartswith` для совпадения начала заголовка;
* `icontains` для частичного совпадения;
* `icontains` для содержимого статьи.

Результаты ранжировать на уровне Python или с помощью аннотаций Django:

1. Точное совпадение заголовка.
2. Заголовок начинается с запроса.
3. Заголовок содержит запрос.
4. Текст содержит запрос.

При росте объёма данных разрешается отдельно внедрить SQLite FTS5, но это не является обязательным для первой версии.

## 8.3. Поисковая выдача

Показывать:

* название статьи;
* фрагмент текста с совпадением;
* дату последнего изменения;
* автора последнего изменения.

## 8.4. Поисковые подсказки

Подсказки появляются после ввода минимум двух символов.

Использовать задержку `debounce` 250–400 мс.

В подсказках искать преимущественно по заголовкам.

# 16. Безопасность

## 16.1. Пароли

Использовать встроенное хеширование Django.

Требования:

* минимальная длина — 12 символов;
* запрет распространённых паролей;
* запрет похожести на email, имя и фамилию;
* запрет полностью цифрового пароля;
* новый пароль не должен совпадать с временным.

## 16.2. Сессии

Для production:

```python
SESSION_COOKIE_SECURE = True
SESSION_COOKIE_HTTPONLY = True
SESSION_COOKIE_SAMESITE = "Lax"
CSRF_COOKIE_SECURE = True
SECURE_SSL_REDIRECT = True
SECURE_HSTS_SECONDS = 31536000
SECURE_HSTS_INCLUDE_SUBDOMAINS = True
SECURE_CONTENT_TYPE_NOSNIFF = True
X_FRAME_OPTIONS = "DENY"
```

HTTPS завершается внешней инфраструктурой размещения, но Nginx в состав проекта не входит.

## 16.3. Защита входа

Ограничивать попытки входа по email.

Не использовать IP-адрес для:

* ограничения попыток;
* блокировки;
* аудита;
* идентификации пользователя.

Требования:

* временная блокировка после серии неудачных попыток для конкретного email;
* журналирование ошибок;
* одинаковое сообщение при неверном email и пароле;
* сброс счётчика после успешного входа;
* не раскрывать существование пользователя.

## 16.4. CSRF и XSS

* Все изменяющие формы защищены CSRF.
* Пользовательский HTML очищается.
* Значения экранируются.
* Опасные URL запрещаются.
* `mark_safe` допускается только для предварительно очищенного HTML.

## 16.5. Изображения

* Проверять фактическое содержимое.
* Не доверять расширению.
* Не хранить изображения на диске.
* Не исполнять содержимое.
* Ограничивать размер запроса.
* Повторно кодировать загруженные изображения.
* Удалять EXIF.
* Отдавать данные только авторизованным пользователям.

## 16.6. Заголовки безопасности

Content Security Policy:

* скрипты только с собственного домена;
* изображения только с собственного домена;
* запрет inline-скриптов;
* запрет встраивания сайта во фреймы;
* ограниченный `connect-src`.

Упоминания S3 и AWS удалить.

# 24. Резервное копирование

Все данные находятся в SQLite:

* пользователи;
* статьи;
* версии;
* изображения;
* миниатюры;
* аудит;
* статистика.

Основной объект резервного копирования:

```text
data/db.sqlite3
```

Резервное копирование должно выполняться корректным способом:

* через SQLite backup API;
* либо через Django management-команду;
* не копировать активный файл простой файловой командой во время записи;
* выполнять проверку целостности;
* хранить минимум 14 ежедневных копий;
* периодически проверять восстановление.

Так как изображения находятся в базе, отдельное резервное копирование media не требуется.
