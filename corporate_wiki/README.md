# Corporate Wiki

Закрытая корпоративная база знаний на Django. Доступ только для
авторизованных сотрудников: просмотр и поиск статей, редактирование с
полной историей версий, сравнение и восстановление версий, изображения
внутри базы данных.

Название и брендинг сайта задаются через переменную окружения `SITE_NAME`
(см. `.env.example`) — в коде и шаблонах они не зашиты.

> Статус: **Этап 1 (инициализация)** — учётные записи, статьи, поиск,
> изображения и остальная функциональность будут добавляться поэтапно
> согласно техническому заданию (`../README.md`).

## Системные требования

* Python 3.12 или новее;
* Docker и Docker Compose (для запуска в контейнере);
* без PostgreSQL, без Nginx, без AWS/S3 — проект их не использует.

## Запуск через Docker

```bash
cp .env.example .env
docker compose up --build
docker compose exec web python manage.py migrate
docker compose exec web python manage.py createsuperuser
docker compose exec web pytest
```

Приложение будет доступно на `http://localhost:8000`.

## Запуск без Docker

```bash
cp .env.example .env
python3.12 -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"

python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
```

## Устройство SQLite и расположение файла базы

Проект использует стандартную SQLite-базу Django — отдельная СУБД не
поднимается. Путь к файлу базы задаётся переменной `SQLITE_PATH`:

* внутри контейнера: `/app/data/db.sqlite3`;
* при локальном запуске без Docker: `data/db.sqlite3` в корне проекта.

В Docker Compose каталог `data/` смонтирован как постоянный volume
(`wiki_data`), поэтому база не теряется при пересборке или перезапуске
контейнера.

Пользовательские изображения **не хранятся на диске** — они будут
храниться непосредственно в SQLite (`BinaryField`), это добавится на
Этапе 6.

## Миграции

```bash
python manage.py makemigrations
python manage.py migrate
```

## Создание администратора

Обычный способ — стандартная команда Django:

```bash
python manage.py createsuperuser
```

Начиная с Этапа 2 появится также management-команда
`create_initial_admin`, которая создаёт первого администратора с
временным паролем из переменных окружения `ADMIN_EMAIL` и
`ADMIN_TEMP_PASSWORD`.

## Запуск тестов

```bash
pytest
coverage run -m pytest
coverage report
```

Настройки тестов используют `config.settings.test` и in-memory SQLite —
реальный файл базы не затрагивается.

## Административный сброс пароля

Начиная с Этапа 2 администратор сможет установить новому или
существующему пользователю временный пароль через Django Admin. После
такого сброса у пользователя автоматически включается принудительная
смена пароля при следующем входе, а все его активные сессии завершаются.
Самостоятельное восстановление пароля (по email) не реализуется.

## Хранение изображений в базе

Начиная с Этапа 6 загруженные пользователями изображения (оригинал и
миниатюра) будут храниться прямо в таблицах SQLite через `BinaryField`,
а не на диске и не во внешнем хранилище. Отдельная папка `media/` в
проекте не создаётся.

## Работа WhiteNoise

Статические файлы приложения (CSS, JavaScript, системные иконки)
обслуживаются через WhiteNoise — отдельный веб-сервер (Nginx и т.п.) не
требуется. Пользовательские изображения WhiteNoise не обслуживает: они
отдаются через отдельные защищённые Django-view.

Перед запуском в production нужно собрать статику:

```bash
python manage.py collectstatic --noinput
```

## Production-запуск

Production-конфигурация (`config.settings.production`) включает:

* `DEBUG=False`;
* обязательный явный `DJANGO_ALLOWED_HOSTS`;
* защищённые cookie сессий и CSRF;
* HSTS и запрет встраивания во фреймы;
* один процесс Gunicorn (`--workers 1`) с несколькими threads — SQLite не
  рассчитан на несколько параллельно пишущих процессов без отдельного
  тестирования блокировок.

Пример запуска:

```bash
DJANGO_SETTINGS_MODULE=config.settings.production gunicorn config.wsgi:application --bind 0.0.0.0:8000 --workers 1 --threads 4
```

TLS терминируется внешней инфраструктурой хостинга — Nginx в состав
проекта не входит.

## Резервное копирование

Все данные (пользователи, статьи, версии, изображения, миниатюры,
аудит) находятся в одном файле — `data/db.sqlite3`. Management-команда
`backup_database` создаёт консистентную копию через SQLite backup API
(а не простое копирование файла во время записи, которое может дать
битый снимок при параллельной записи) и проверяет её целостность через
`PRAGMA integrity_check`; если проверка не пройдена, битый файл копии
удаляется, а команда завершается с ошибкой.

```bash
python manage.py backup_database
```

Копия сохраняется в `BACKUP_DIR` (по умолчанию — папка `backups` рядом
с файлом базы) с именем вида `db-backup-<UTC-время>.sqlite3`. Команду
можно безопасно запускать, пока приложение обслуживает запросы —
например, по расписанию (cron/systemd timer) на хосте, где развёрнут
контейнер.

## Восстановление базы

Восстановление выполняется остановкой приложения и заменой файла
`data/db.sqlite3` (или volume `wiki_data`) на проверенную резервную
копию, после чего приложение запускается заново.

## Ограничения SQLite

* Рекомендуется один процесс/worker, активно пишущий в базу; параллельная
  запись из нескольких процессов не тестировалась и не поддерживается
  в первой версии.
* Уникальность заголовка статьи без учёта регистра обеспечивается на
  уровне сервисного слоя, а не средствами полнотекстового поиска СУБД.
* Поиск реализован средствами Django ORM (`icontains`, `istartswith`,
  `iexact`) без использования PostgreSQL-специфичных возможностей.
